Assignment goals

1. Movie search
- Add a search input to the main screen.
- Search movies by keyword through the OMDb web API.
- Reference request: https://www.omdbapi.com/?apikey=<API_KEY>&s=<SEARCH_TERM>
- Display search results in a scrollable list using LazyColumn or RecyclerView.
- Show clear loading, empty-result, and error states.
- Do not commit a real API key. Read it from a local, ignored configuration value and expose it to the app through BuildConfig or another safe build-time mechanism.

2. Movie details
- Make every movie result selectable.
- Open a details screen when a result is selected.
- Display at least the movie title and poster.
- Display the movie type when it is available.

3. Favorites
- Allow a movie to be added to and removed from Favorites.
- Provide an accessible Favorites list in the app.
- Persist favorites locally so they survive process death and app restarts.
- Room is the recommended persistence solution.

4. Advertising SDK module
- Create a separate Gradle module named :sdk.
- Keep all ad-related implementation and state inside this module.
- Expose a small API that the :app module can use without depending directly on provider-specific details.
- Implement Google AdMob interstitial ads.
- Implement Google AdMob native ads.
- Design an ad-provider interface or equivalent abstraction so another provider can be added later without rewriting the app UI.
- Use Google test ad unit IDs during development and automated testing. Do not commit private production identifiers or secrets.

5. Native-ad placement
- Mix native ads into the main search-result list at indexes 1 and 3.
- Add only positions that are valid for the available result count; do not crash on short lists.
- The assignment wording is ambiguous because zero-based index 3 needs at least four items, while it mentions at least three results. Document the chosen interpretation in the README and cover the placement logic with unit tests.
- Use separate UI models for movie rows and ad rows so list rendering remains type-safe and testable.

6. Interstitial behavior
- Show an interstitial ad only when the user returns to the app for the second time.
- Define "returns to the app" consistently as a foreground session or launch, document that decision, and persist the counter so rotation and process recreation do not trigger the ad incorrectly.
- Do not show the interstitial repeatedly after the second qualifying return unless the requirement is clarified.

7. Code quality and delivery
- Keep packages, class names, and responsibilities easy to understand.
- Separate UI, domain/state, data, database, network, and advertising responsibilities.
- Handle API and image failures without crashing.
- Add meaningful unit tests for search mapping/state, favorite persistence behavior, ad insertion positions, and second-return logic.
- Add UI or instrumentation tests for the main user flows where practical.
- Add a README with setup instructions, API-key configuration, architecture notes, assumptions, screenshots, and build/test commands.
- Publish the finished source in a public GitHub repository.
